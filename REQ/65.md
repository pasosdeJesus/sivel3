---

## 1. Objective

Let the public site (`apps/nextjs`) run **without the Rails app (`sivel2/`) being
up**, by replacing the two Next.js routes that still proxy to Rails with Next.js
API routes that read the shared PostgreSQL database directly with Kysely, using
the same tables the Rails app uses.

After this, Rails remains available **only as an optional backoffice** (data
entry / admin UI), exactly as learn.tg did in R-#233: "Rails stopped in
production; kept as a backoffice". The public site no longer makes any HTTP
request to Rails.

---

| Env var | Declared in | Code references |
|---|---|---|

There are **no Rails tests** for the two endpoints either
(`sivel2/test/controllers/**` only covers the MSIP admin controllers).

### What Rails still owns (kept, not removed)

- The backoffice admin UI: MSIP + Devise + the `Cor1440Gen`, `Mr519Gen`,
  `Heb412Gen`, `Sivel2Gen` engines mounted in `sivel2/config/routes.rb`.
- The migrations for the Rails-owned tables (`msip_*`, `sivel2_gen_*`,
  `heb412_*`, `mr519_*`) and the `structure.sql` / `db.d.ts` sync hook
  (`sivel2/lib/tasks/db_migrate_hook.rake`).
- The materialized views `sivel2_gen_conscaso` / `sivel2_gen_consexpcaso`
  (DB-side objects; they survive regardless of Rails).

None of these are needed for the public site to serve `/cases` and the map.

## 3. Options

### Option 1 — Keep the proxy

Leave the two routes as-is; keep Rails running in production.

- **Pros:** zero code change.
- **Cons:** the two public endpoints go down whenever Rails is down; requires
  running and monitoring Rails (port 3500) in production; keeps a CORS +
  cross-origin dependency; the last blocker to a "Next-only" runtime.
- **Effort:** 0h.

### Option 2 — Next.js API reading the shared DB (recommended)

Replace the two proxies with Kysely queries. This is the learn.tg R-#183 pattern
applied to the two remaining routes.

- **Pros:** no Rails runtime for the public site; same renderer (Next) for all
  data; no CORS; reuses `db.d.ts` types.
- **Cons:** the filter/serialization logic that lived in the Rails
  `Sivel2Gen::Concerns::Controllers::CasosController` + jbuilder templates must be
  reimplemented in SQL (bounded: 5 filters, 2 JSON shapes).
- **Effort:** ~1 day (see §9).

**Recommendation:** Option 2.

## 4. Design of the replacement endpoints

### 4.1 `GET /api/cases/datos-osm` (map markers)

**Current Rails output** (from
`sivel2_gen/app/views/sivel2_gen/casos/repmapaosm.json.jbuilder`, with the fixed
params the Next proxy sends: `filtro[inc_ubicaciones]=2`, `filtro[inc_fecha]=1`):

```json
{
  "casos": 1234, "victimas": 2345, "actos": 3456, "victimizaciones": 4567,
  "respuesta": {
    "<caso_id>": {
      "latitud": "<string>",
      "longitud": "<string>",
      "departamento": "<nombre>",
      "municipio": "<nombre>",
      "fecha": "<yyyy-mm-dd>"
    }
  }
}
```

The frontend (`apps/nextjs/components/mapa/MapComponent.tsx:171-207`) only uses
`respuesta[code].latitud` / `.longitud` and the key; it fetches the counts
separately from `/api/cases/counts`. The `filtro[disgenera]` and `idplantilla`
params the proxy adds are irrelevant to this action.

**Replacement query** (Kysely, one pass):

```sql
SELECT c.id AS caso_id, u.latitud, u.longitud,
       d.nombre AS departamento, m.nombre AS municipio, c.fecha
FROM sivel2_gen_caso c
JOIN msip_ubicacion u ON u.caso_id = c.id
LEFT JOIN msip_departamento d ON d.id = u.departamento_id
LEFT JOIN msip_municipio    m ON m.id = u.municipio_id
WHERE u.latitud IS NOT NULL AND u.longitud IS NOT NULL
  [AND c.fecha >= :fechaini] [AND c.fecha <= :fechafin]
  [AND u.departamento_id = :departamento_id]
  [AND EXISTS (SELECT 1 FROM sivel2_gen_caso_presponsable cp
               WHERE cp.caso_id = c.id AND cp.presponsable_id = :presponsable_id)]
  [AND EXISTS (SELECT 1 FROM sivel2_gen_acto a
               WHERE a.caso_id = c.id AND a.categoria_id = :categoria_id)]
```

Filters are exactly the five keys the frontend already sends and
`/api/cases/counts` already parses
(`apps/nextjs/app/[locale]/cases/osmmap/hooks/useOSMMapData.ts:11-15`):
`filtro[fechaini]`, `filtro[fechafin]`, `filtro[departamento_id]`,
`filtro[presponsable_id]`, `filtro[categoria_id]`.

Return the **same envelope** `{ respuesta: { <id>: { latitud, longitud, ... } } }`
so the frontend needs no change. `latitud`/`longitud` stay strings (the frontend
`parseFloat`s them).

### 4.2 `GET /api/cases/[id]` (case detail)

**Current Rails output** (from
`sivel2_gen/app/views/sivel2_gen/casos/_caso.json.jbuilder` via `show.json.jbuilder`):

```json
{
  "caso": {
    "id": 123,
    "titulo": "...",         // if present
    "hechos": "...",         // = sivel2_gen_caso.memo
    "fecha": "2024-01-01",
    "hora": "...",
    "departamento": "...",
    "municipio": "...",
    "centro_poblado": "...",
    "lugar": "...",          // only when msip_ubicacion.tsitio_id == 3
    "presponsables": { "<id>": "<nombre>" },
    "victimas": { "<id>": "<nombres apellidos>" }
  }
}
```

The TypeScript contract the frontend uses
(`components/mapa/MapComponent.tsx:54-67`, interface `CasoDetalle`) types
`victimas`/`presponsables` as **`string[]`** and calls `.map(...)` on them
(lines 537, 549). Because Rails emits **objects** keyed by id, that call is
guarded by `.length > 0`, which is `undefined` for an object, so the
victims/perpetrators lists silently never render today. The Next rewrite should
return **arrays of strings** (matching `CasoDetalle`) — this fixes the latent bug
as a side effect.

**Replacement sources:**

- `sivel2_gen_conscaso1` — a **plain VIEW** already present in the shared schema
  and already typed in `apps/nextjs/db/db.d.ts:1037` (`Sivel2GenConscaso1`:
  `caso_id, fecha, memo, ubicaciones, victimas, presponsables, tipificacion`).
  It aggregates victim names, perpetrator names and the `"Depto / Municipio"`
  string with `array_to_string`, so the DB does the heavy lifting.
- `sivel2_gen_caso` — `titulo`, `hora`, `memo`, `ubicacion_id`.
- `msip_ubicacion` (by `caso.id` or `caso.ubicacion_id`) — `lugar`, `tsitio_id`,
  `departamento_id`, `municipio_id`, `centropoblado_id`.
- `msip_departamento` / `msip_municipio` / `msip_centropoblado` — names.
- `sivel2_gen_victima JOIN msip_persona` — victim names (if we want an array
  rather than the `conscaso1.victimas` concatenated string).
- `sivel2_gen_caso_presponsable JOIN sivel2_gen_presponsable` — perpetrator names.

Return `{ caso: { ... } }` with `victimas: string[]` and
`presponsables: string[]`.

### 4.3 Auth

Both endpoints are **public read-only** (they expose already-public case data,
like `/api/cases/counts`). No session, no signature, no token. `NEXT_PUBLIC_API1`
was never an auth boundary.

### 4.4 Why `sivel2_gen_conscaso1` and not the materialized `conscaso`

`sivel2_gen_conscaso1` is a plain view (no refresh needed). The materialized
`sivel2_gen_conscaso` / `consexpcaso` require
`REFRESH MATERIALIZED VIEW` and are used by the Rails reports; the public map and
detail endpoints do not need them.

## 8. Risks and mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| SQL reimplementation diverges from Rails filters/serialization | Medium | Medium | Port filter by filter; add tests asserting the same JSON envelope; compare against Rails output once before retiring the proxy |
| `sivel2_gen_conscaso1` view absent in a non-migrated DB | Low | High | It lives in the shared schema (`apps/nextjs/db/structure.sql:4231`); add a migration/assert that the view exists |
| Victims/perpetrators shape change breaks a consumer | Low | Low | Only `MapComponent` consumes it; the change (`object` → `string[]`) fixes the current display; covered by tests |
| Case detail needs fields not in `conscaso1` (e.g. `hora`, `lugar`) | Low | Low | `sivel2_gen_caso` + `msip_ubicacion` joins in §4.2 |
| A hidden Rails dependency appears at runtime | Low | Medium | Sweep `git grep -nE 'NEXT_PUBLIC_API1|:3500|:9001|sivelxyz-admin' -- apps`; run with Rails stopped before decommissioning |

Rollback: revert the two route files and re-add `NEXT_PUBLIC_API1`; the proxy is a
one-commit change.
