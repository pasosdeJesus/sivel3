## 1. Objective

Give sivel3 the same **two-layer test system** learn.tg uses, runnable with
`bin/m test:e2e`:

1. **Unit tests** (vitest) — already present, realigned to the shared mocks
   published by `@pasosdejesus/m/test-utils` (learn.tg convention).
2. **E2E tests** — new: `e2e/smoke/*.spec.mjs` (HTTP, no browser) and
   `e2e/specs/*.spec.mjs` (Puppeteer).

The e2e suite is also the **regression guard for R-#65** ("not requiring the
Rails app running"): a smoke spec must prove the public site works with Rails
down.

This REQ is organised in two blocks, mirroring the board (`m/REQ/36` §2.1/§2.3):

- **Block A — do now** (no dependency on `m`): scaffolding, smoke specs, Makefile
  targets, docs, unit-test alignment.
- **Block B — blocked on `m` items 1, 2, 4, 5**: browser specs and the signature
  specs (`SITE_URL`, `retry`, real signing).

### Findings (fixed for the dev/prod test)

- **Connection-pool leak** (fixed): `newKyselyPostgresql()`
  (`apps/nextjs/.config/kysely.config.ts`) created a new `pg.Pool` per call and
  never ended it; under repeated requests Postgres answered `sorry, too many
  clients already`, so `/api/cases/counts` (and others) returned 500. Now a single
  process-wide pool on `globalThis` is shared by every caller
  (`tests/kysely-pool.test.ts` guards it). Verified with a 42-request burst →
  all 200.
- **Map white-screen** (fixed): `components/CountsPopover.tsx` called
  `counts.casos.toLocaleString()` (and 3 siblings) without guarding, so a failed
  counts fetch crashed the whole tree; `components/mapa/MapComponent.tsx` passed
  the error body to it. Now `MapComponent` only propagates an `ok` payload and
  `CountsPopover` defaults missing counts to 0. The map route now renders fully
  in the browser (verified with the shared Puppeteer launcher).
- **Migrations run on the local dev DB** (2026-10-08): the DB had the schema
  (loaded from `db/structure.sql`) but an **empty `kysely_migration`**, because
  `db:structure:dump` is `pg_dump --schema-only` (never carries the
  `kysely_migration` rows) and the dump predated the last two migrations
  (`feedback`, `citizen_notes`). Reconciled: baselined the 17 migrations already
  reflected in the dump, then `bin/m db:migrate` applied
  `20260622_add_feedback_to_pre_alert` and
  `20260625_add_citizen_notes_to_pre_alert` (`kysely_migration` now 19 rows;
  `/api/pre-alerts` 200). The migrate post-tasks also **regenerated
  `db/structure.sql`** (now includes both columns) and `db/db.d.ts` (unchanged).
  **Fresh dev/staging DBs need the same baseline** (or run migrations against the
  Rails-provisioned DB) — loading only the schema dump leaves every migration
  "pending".
- **`M_POST_MIGRATE` hook fails here**: `.env` runs
  `cd ../../sivel2 && bin/rails db:schema:dump` after migrating; the Rails app is
  not provisioned in this environment (bundler cannot resolve gems), so the hook
  exits 1. The Kysely migrations themselves succeeded; the hook only refreshes the
  Rails schema dump.
- **Restored the dev-site dump** (`bin/m db:restore oct9`, `db/backups/oct9/`,
  directory format). The local DB now mirrors dev: 531 casos, 896 víctimas, 1011
  actos, 54 pre-alertas (51 pending/2 converted/1 reserved), `kysely_migration`
  = 19 (consistent — no baseline needed). smoke 4/4 and specs 4/4 against it;
  `prealert-buy` positive path (reserve a pending id) also green.
- **Dev site runs an older build**: `https://sivel.xyz:9001` serves 200 and renders,
  but the DOM has **no `data-testid`** (my `ConnectWalletButton` testids are not in
  that bundle), so the browser specs fail there; smoke passes (it does not need
  testids). Under a 60-request burst the dev site still returns 500 (the pool leak
  is present), i.e. it predates the pool/`CountsPopover` fixes. **Redeploy the dev
  site from the current sivel3 code** before running the browser specs there.
