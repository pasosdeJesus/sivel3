## Description

Implement the user interface and messaging system for notifications generated by the state machine (#46). This includes:

- **In‑app notifications** (bell icon, dropdown list, mark as read)
- **Email digests** (daily summary, optional)
- **User preferences** (opt‑in/opt‑out for email)

This issue does **not** define what triggers a notification — that logic lives in #46.

**Future‑ready design:** This issue lays the foundation for a broader communication system (comments, feedback, collaboration). The database schema and API design are extensible to support future features without breaking changes.

## 📬 Current Scope (MVP)

### 1. In‑App Notifications

| Component | Description |
|-----------|-------------|
| **Notification Bell (🔔)** | Located in the top navigation bar. Shows a badge with the count of unread notifications. |
| **Dropdown** | Clicking the bell opens a dropdown list of recent notifications (last 20). Each notification includes: icon, title, message, timestamp, and link. |
| **Notification Center** | Full page at `/notifications` with paginated list, filters (`all`, `unread`, `read`), and actions (mark individual as read / mark all as read). |

- Daily email at 8:00 AM with summary of notifications from last 24h.
- Requires SMTP infrastructure + job queue (deferred).
- User can opt‑in/opt‑out in their profile settings.

### 3. User Preferences (Post‑MVP)

- Settings page: toggle for email digests (on/off)
- Default: email digests enabled
- Deferred until email infrastructure is in place.

## 🏗️ Database Schema (MVP)

### `notifications` table

```sql
CREATE TABLE notifications (
    id SERIAL PRIMARY KEY,
    wallet VARCHAR(42) NOT NULL,
    type VARCHAR(30) NOT NULL,
    title TEXT NOT NULL,
    message TEXT NOT NULL,
    link TEXT,
    is_read BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_notifications_wallet ON notifications(wallet);
CREATE INDEX idx_notifications_unread ON notifications(wallet) WHERE is_read = FALSE;
```

**Design notes:**
- `type` field allows filtering and different icon rendering
- `link` field enables deep linking to the relevant resource (pre‑alert, alert, case)
- `is_read` supports unread counts and marking as read
- Indexes ensure performance as the table grows

## 🔌 API Endpoints (MVP)

### 1. GET `/api/notifications`

Returns the current user's notifications (paginated).

**Query params:**
- `limit` (default 20)
- `offset` (default 0)
- `filter`: `all`, `unread`, `read`

**Response:**
```json
{
  "notifications": [
    {
      "id": 1,
      "type": "pre_alert_bought",
      "title": "Pre‑alerta comprada",
      "message": "Has comprado la pre‑alerta #42...",
      "link": "/pre-alerts/42",
      "is_read": false,
      "created_at": "2026-06-24T10:00:00Z"
    }
  ],
  "total": 42,
  "unread_count": 5
}
```

### 2. POST `/api/notifications/:id/read`

Mark a single notification as read.

### 3. POST `/api/notifications/read-all`

Mark all notifications as read.

### 4. PUT `/api/user/preferences`

Update user preferences (email digest on/off).

## 🧩 Integration with #46 (State Machine)

The notification logic (what triggers a notification) lives in #46. This issue (#40) only implements the UI and delivery mechanisms.

### Events that trigger notifications (from #46)

| Event | Trigger | Recipient | Notification type |
|-------|---------|-----------|-------------------|
| Pre‑alert bought | `Pending → Reserved` | Buyer | `pre_alert_bought` |
| New info available | `NeedsMoreInfo → PendingWithAdditionalInfo` | Buyer (if reserved) | `new_info_available` |
| Conversion deadline approaching | 24h before `Reserved → Expired` | Buyer | `conversion_reminder` |
| Pre‑alert expired | `Reserved → Expired` | Buyer | `pre_alert_expired` |
| Alert scored | `UnderReview → ScoredByDocumenter` | Citizen (buyer) | `alert_scored` |
| Payment received | `ScoredByDocumenter → Paid` | Citizen (buyer) | `payment_received` |
| New alert in queue | `ConvertedByCitizen → UnderReview` | Documenters | `new_alert_ready` |
| Alert marked NeedsMoreInfo | `UnderReview → NeedsMoreInfo` | Documenter | `alert_needs_review` |

## 🖌️ UI Components

### 1. Notification Bell

```tsx
// components/NotificationBell.tsx
export function NotificationBell() {
  const { unreadCount, notifications } = useNotifications();
  
  return (
    <Popover>
      <PopoverTrigger>
        <BellIcon />
        {unreadCount > 0 && <Badge>{unreadCount}</Badge>}
      </PopoverTrigger>
      <PopoverContent>
        {notifications.slice(0, 20).map(notification => (
          <NotificationItem key={notification.id} {...notification} />
        ))}
        <Link href="/notifications">Ver todas</Link>
      </PopoverContent>
    </Popover>
  );
}
```

### 2. Notification Center

```tsx
// app/notifications/page.tsx
export default function NotificationsPage() {
  const { notifications, unreadCount, markAsRead, markAllAsRead } = useNotifications();
  
  return (
    <div>
      <Header>
        <h1>Notificaciones</h1>
        <Button onClick={markAllAsRead}>Marcar todas como leídas</Button>
      </Header>
      <FilterTabs filters={['all', 'unread', 'read']} />
      <NotificationList notifications={notifications} onMarkAsRead={markAsRead} />
    </div>
  );
}
```

## 📝 Notes for the Developer

- **Extensibility:** The `notifications` table is designed to support future communication features (comments, feedback, messages). Additional tables can be added without changing the notification schema.
- **Performance:** Use indexes on `wallet` and `is_read`. Paginate notifications (max 20 per page).
- **Email:** Use a queued job system (e.g., BullMQ, Sidekiq) to send emails asynchronously.
- **Localization:** All notification titles and messages should be in Spanish (for MVP). English support can be added later.
