# R-#10: R-#10 Build the Case Verification Workflow (Documenter & Validator Dashboards)

Once citizen alerts are submitted (via the pre‑alert market, see #8) and roles are defined (see #9), we need the actual verification workflow. This involves a dashboard for `Documenters` to review alerts, convert them into structured cases, and submit them for peer review. A separate dashboard for the `Publishing Validator` will allow the final audit and blockchain certification.

The workflow is as follows:

1.  **Citizen submits an improved alert** (converted from a pre‑alert, status = `PENDING`).
2.  **Documenter reviews the alert** (access restricted by `Documenter` SBT, see #9).
3.  **Documenter converts the alert into a case** (integrates with `sivel2` Rails backend).
4.  **Case enters peer review** (assigned to another `Documenter`).
5.  **Peer reviewer approves or rejects**.
6.  **If approved, case goes to `Publishing Validator`** (access restricted by `Validator` SBT).
7.  **Validator performs final audit and triggers blockchain certification** (via `CaseCertification.sol` contract, see #4).

All actions are logged for transparency and auditability.

---

## Key Design Decisions

| Decision | Rationale |
| :--- | :--- |
| **Access control via SBTs** | Only wallets holding the `Documenter` SBT (see #9) can access the documenter dashboard. Only wallets holding the `Validator` SBT can access the validator dashboard. |
| **Role‑based API protection** | API endpoints check the user’s SBT before processing requests. |
| **Peer review before validation** | Adds an extra layer of quality control and distributes workload among documenters. |
| **Integration with existing `sivel2` case structure** | Reuses the mature case model from the legacy Rails app, avoiding duplication. |
| **Audit trail** | All status changes are logged with a timestamp and the user’s wallet address. |

## Tasks

### 1. Database Changes

Add necessary columns to the `citizen_alert` table to support the verification workflow:

```sql
ALTER TABLE citizen_alert
ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'PENDING', -- PENDING, IN_REVIEW, CONVERTED, REJECTED
ADD COLUMN assigned_documenter_id INTEGER REFERENCES usuario(id),
ADD COLUMN case_id INTEGER, -- ID of the case created in sivel2
ADD COLUMN peer_reviewer_id INTEGER REFERENCES usuario(id),
ADD COLUMN peer_review_status VARCHAR(20), -- PENDING, APPROVED, REJECTED
ADD COLUMN validator_id INTEGER REFERENCES usuario(id),
ADD COLUMN certified_at TIMESTAMP,
ADD COLUMN rejection_reason TEXT,
ADD COLUMN updated_at TIMESTAMP NOT NULL DEFAULT NOW();
```

Create a `case_review_log` table to track the review steps (audit trail):

```sql
CREATE TABLE case_review_log (
    id BIGSERIAL PRIMARY KEY,
    citizen_alert_id INTEGER NOT NULL REFERENCES citizen_alert(id),
    action VARCHAR(50) NOT NULL, -- ASSIGNED, STARTED_REVIEW, CONVERTED, PEER_APPROVED, PEER_REJECTED, VALIDATOR_APPROVED, VALIDATOR_REJECTED, CERTIFIED
    actor_wallet VARCHAR(42) NOT NULL,
    actor_role VARCHAR(20) NOT NULL, -- DOCUMENTER, VALIDATOR
    details TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

### 2. API Endpoints (Role‑Protected)

All endpoints must verify that the caller holds the required SBT (see #9).

| Endpoint | Method | Role Required | Description |
| :--- | :--- | :--- | :--- |
| `GET /api/alerts/pending` | GET | `DOCUMENTER` | Returns list of pending alerts assigned to the documenter (based on region). |
| `POST /api/alerts/:id/assign` | POST | `DOCUMENTER` | Assigns an alert to the current documenter. |
| `POST /api/alerts/:id/start-review` | POST | `DOCUMENTER` | Marks an alert as `IN_REVIEW` (prevents double work). |
| `POST /api/alerts/:id/convert` | POST | `DOCUMENTER` | Converts an alert into a case (calls `sivel2` API). Creates a case and updates `case_id` and status to `CONVERTED`. |
| `POST /api/alerts/:id/reject` | POST | `DOCUMENTER` | Rejects an alert with a reason. |
| `GET /api/cases/pending-peer-review` | GET | `DOCUMENTER` | Lists cases that need peer review (excludes cases created by the caller). |
| `POST /api/cases/:id/peer-review` | POST | `DOCUMENTER` | Approves or rejects a case during peer review. |
| `GET /api/cases/pending-validation` | GET | `VALIDATOR` | Lists cases pending final validation. |
| `POST /api/cases/:id/validate` | POST | `VALIDATOR` | Approves or rejects a case. If approved, triggers blockchain certification (see #4). |

### 3. Documenter Dashboard (`/dashboard/documenter`)

Create a dashboard accessible only to wallets holding the `Documenter` SBT.

- **Alert List:** Table of pending alerts assigned to the documenter (by region). Columns: Alert ID, Title, Date Submitted, Status, Actions.
- **Alert Detail View:** Shows full alert details (original pre‑alert data + citizen improvements). Includes images, location map, and timeline.
- **Actions:**
    - **Start Review:** Locks the alert so no other documenter can work on it.
    - **Convert to Case:** Opens a form to create a case in `sivel2`. The form should pre‑fill data from the alert and allow the documenter to add structured case information (victims, acts, perpetrators, etc.). After submission, calls `POST /api/alerts/:id/convert` and redirects to the case view.
    - **Reject:** Requires a reason and moves the alert to a rejected state.

- **Case List:** Table of cases the documenter has converted, with their current status (PENDING_PEER_REVIEW, PEER_APPROVED, PEER_REJECTED, PENDING_VALIDATION, CERTIFIED).

### 4. Peer Review Dashboard (`/dashboard/peer-review`)

Create a dashboard for documenters to review cases submitted by their peers.

- **Case List:** Table of cases pending peer review (excludes cases created by the current documenter). Columns: Case ID, Title, Original Documenter, Date Submitted.
- **Case Detail View:** Shows the full case data (as it would appear in `sivel2`).
- **Actions:**
    - **Approve:** Case moves to the Publishing Validator dashboard. Status becomes `PENDING_VALIDATION`.
    - **Reject:** Case is sent back to the original documenter with required changes. Status becomes `PEER_REJECTED`.

### 5. Publishing Validator Dashboard (`/dashboard/validator`)

Create a dashboard accessible only to wallets holding the `Validator` SBT.

- **Case List:** Table of cases pending validation. Columns: Case ID, Title, Documenter, Peer Reviewer, Date Approved.
- **Case Detail View:** Shows the full case data.
- **Actions:**
    - **Approve:** Triggers blockchain certification (calls `certifyCase` on `CaseCertification.sol`, see #4). Marks case as `CERTIFIED` and stores the transaction hash.
    - **Reject:** Sends case back to the peer review stage with comments.

### 6. Integration with `sivel2` (Rails Backend)

Converting an alert to a case requires creating a new case in the legacy `sivel2` Rails application.

- **Create an internal API in `sivel2`:** `POST /api/cases` that accepts case data (victims, acts, location, etc.) and returns the new `case_id`.
- **In `sivel.xyz` Next.js API (`POST /api/alerts/:id/convert`):**
    1.  Fetch the alert data.
    2.  Transform the alert data into the format expected by the `sivel2` API.
    3.  Call the `sivel2` API to create the case.
    4.  Store the returned `case_id` in the `citizen_alert` table.
    5.  Update the alert status to `CONVERTED`.
    6.  Log the action in `case_review_log`.

### 7. Blockchain Certification (Validator Action)

When a validator approves a case, the system must certify it on‑chain.

- **Contract:** `CaseCertification.sol` (see #4) with a function `certifyCase(bytes32 caseHash, uint256 caseId)`.
- **Integration:** In `POST /api/cases/:id/validate` (when action = approve):
    1.  Fetch the full case data from `sivel2`.
    2.  Generate a SHA‑256 hash of the case data (using a deterministic method).
    3.  Call the `certifyCase` function on the `CaseCertification` contract (using the `PRIVATE_KEY` of the `sivel.xyz` backend wallet, which must have the `CERTIFIER_ROLE`).
    4.  Store the transaction hash in the `citizen_alert` table (or a new `case_certification` table).
    5.  Update the case status to `CERTIFIED`.

## Acceptance Criteria

- [ ] A `Documenter` with the appropriate SBT can see pending alerts assigned to their region.
- [ ] The `Documenter` can convert an alert into a full case, which is successfully created in the `sivel2` Rails backend.
- [ ] After conversion, the case enters the `Peer Review` dashboard and is visible to other documenters.
- [ ] A `Peer Reviewer` can approve or reject a case.
- [ ] If approved, the case moves to the `Publishing Validator` dashboard.
- [ ] A `Validator` with the appropriate SBT can approve a case, which triggers the blockchain certification (see #4) and stores the transaction hash.
- [ ] All status changes are logged in the `case_review_log` table with the actor’s wallet address and role.
- [ ] API endpoints return `403 Forbidden` when called by a wallet without the required SBT role.
