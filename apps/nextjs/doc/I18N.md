# Internationalization (i18n) Guide — SIVeL 3

This document explains how internationalization is implemented in the Next.js
application and provides guidelines for developers to maintain and extend it.

---

## 1. Routing and Language Detection

We use a **sub-path routing** strategy with a dynamic segment `[locale]`.

*   **Middleware (`middleware.ts`):** Detects the user's preferred language via
    the `accept-language` header and redirects to the appropriate sub-path
    (e.g., `/` -> `/es/`). API routes (`/api/*`) and static assets are excluded.
*   **Supported locales:** `en` (English) and `es` (Spanish). Any other locale
    in the URL returns 404 via `app/[locale]/layout.tsx`.

---

## 2. Translation Pattern: Zero-Dependency TypeScript

The project follows a **zero-dependency, local TypeScript pattern** for
internationalization.

**Why?** Traditional i18n libraries (`next-i18next`, `next-intl`) have shown
compatibility or performance issues on **OpenBSD/adJ**. Pure TypeScript objects
give maximum performance, zero external dependencies, and full type safety.

### Pattern: Local TypeScript Objects

Each component or feature file contains its own translation object.

*   **Location:** Inside the same `.tsx` or `.ts` file of the component/feature.
*   **Pattern:**

    ```typescript
    const localTranslations = {
      en: { title: 'Hello', description: 'World' },
      es: { title: 'Hola', description: 'Mundo' }
    };
    ```

#### A. Usage in Client Components (with Hook)

```tsx
'use client';
import { useTranslation } from '@/hooks/useTranslation';

export function MyComponent() {
  const { t, locale } = useTranslation(localTranslations);
  return <h1>{t('title')}</h1>;
}
```

#### B. Usage in Server Components (Universal)

Server components cannot use hooks. Use the pure function `createTranslator`
and pass the `locale` from the page params.

```tsx
import { createTranslator } from '@/hooks/useTranslation';

export default async function ServerPage({ params }: { params: { locale: string } }) {
  const { locale } = await params;
  const t = createTranslator(locale as 'en' | 'es', localTranslations);

  return <h1>{t('title')}</h1>;
}
```

> `createTranslator` also accepts an optional third argument `common` for
> fallback terms (automatically injected by the hook — see §3 below).

---

## 3. Global Translations (Common Terms)

Terms used across the entire application (e.g., "Cases", "Date", "Department")
live in a central TypeScript module:

```
lib/i18n/common.ts
```

This module is **pure data** — no framework imports, designed to be migratable
to `@pasosdejesus/m`. Both `createTranslator` and the `useTranslation` hook
fall back to these common terms through the following resolution order:

1. Local translations in the requested locale (`translations['es']` or `translations['en']`)
2. Local translations in English (`translations['en']`)
3. Common terms in the requested locale (`common['es']` or `common['en']`)
4. Common terms in English (`common['en']`)
5. The raw key as last resort

This means a component only needs to define its component-specific strings;
shared labels are picked up from `lib/i18n/common.ts` automatically.

---

## 4. Step-by-Step: Adding a New Language String

1.  **Identify the scope.** Is this term used in a single component or
    across the app?
    *   **Single component:** Add inline to the local translations object.
    *   **Global:** Add to `lib/i18n/common.ts`.

2.  **Add the key in both `en` and `es`** to maintain parity.

3.  **Use in component** via `t('key')` from the hook or `createTranslator`.

---

## 5. Best Practices

*   **Parity:** Always add keys to all supported languages simultaneously.
*   **Placeholders:** Use `{{0}}`, `{{1}}`, etc. for dynamic content. Pass
    arguments after the key: `t('greeting', name)`.
*   **Types:** Use `keyof typeof translations.en` for type-safe key references.
*   **Independence:** When adding a new `lib/i18n/` module, keep it framework-
    free so it can migrate to `@pasosdejesus/m` later.
